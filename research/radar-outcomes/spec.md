# Radar outcome scorer: spec

Approved 2026-10-24 and built as `backend/scripts/radar_outcomes.py` with `backend/tests/test_radar_outcomes.py`. Scheduled the same day, with the owner's approval: a weekly Friday timer on the VPS runs the scorer and the review ([Radar, Outcome scoring](../../docs/radar.md#outcome-scoring)).

## The question

When Radar flags a stock or group, does the move keep going in the flagged
direction, compared with SPY, more than it does for the top names on the plain
Movers list at the same minute?

- **Radar beats Movers:** its rules add timing value, and phone alerts (R1)
  have evidence behind them.
- **Radar ties Movers:** its value has to come from breadth, news and context
  (your ratings), not from catching moves early.
- **Radar does worse:** its events mark exhaustion. That is a fade signal,
  which is also worth knowing.

This is signal quality, not P&L. It uses no costs, no option prices and no
trades.

## What it scores

- **Events:** every event Radar actually wrote live, at its first-seen pass.
  Revisions are ignored, because the first sighting is what you would have
  seen. Events are not regenerated by replay.
- **Outcome:** the return over the following period, minus SPY's, signed so
  that positive means "kept going in the flagged direction".
  - Price: the recorded quote `last`, using only quotes the rules themselves
    would accept (trade at most 120 s old).
  - Horizons: **+30 min, +60 min (primary), session close.** Each is the pass
    nearest the target within ±2 minutes, or the session's last pass for the
    close. A missing endpoint is excluded and counted.
  - Group events: the equal-weight average of their members' outcomes.
- **Comparison 1, Movers (the one that matters):** at the same pass, the plain
  "Movers now" ranking (`radar_movers.build_movers`, unchanged). Use the top
  10 leaders for an up event, the top 10 laggards for a down event, excluding
  the event's own symbols. Same outcome measure.
- **Comparison 2, random:** 5 tracked stocks drawn at the same pass, with a
  seed derived from the event id, signed in the event's direction. This
  should average about zero; it checks the plumbing and shows the noise
  level.

## The read-out

Reported per rule version, never pooled across versions:

| | Events | Kept going (hit rate) | Mean signed rel. return | Movers mean | Radar − Movers (95% range) |
|---|---|---|---|---|---|
| +30 min / +60 min / close | | | | | |

- The range comes from resampling **by session**, because events on the same
  day share the market.
- Exclusions are counted by reason: no endpoint, stale quote, or too late in
  the day for the horizon.

## Decision, fixed now

Review once, using the **first 20 verified recorded sessions of one frozen
configuration**. The October 28 metadata audit found v0 active and no v1 events;
the earlier expected v1 start was not activation evidence. This repair does not
change `RADAR_RULES_VERSION`. Missing legacy provenance cannot be backfilled by
replay.

- **Radar beats Movers:** at +60 min, Radar − Movers is above 0 with its
  whole 95% range above 0, and the event hit rate is above 50%.
- **Radar does worse:** the whole range is below 0.
- **Otherwise:** no demonstrated timing value. This is the likely honest
  outcome on about 80 stock events, and it is still a useful answer.
- No threshold changes because of these numbers within a version. A new rule
  version starts a new count.
- v0's October 22–23 calibration sessions are reported, labelled in-sample,
  and kept out of the decision.

## How it runs

```bash
python -m scripts.radar_outcomes /abs/path/radar.sqlite --out /var/lib/tradejournal/radar/outcomes.jsonl
```

- **Read-only on the Radar store.** It opens the existing
  `RadarStore(read_only=True)` with SQLite `mode=ro`, so it cannot block or
  alter the recorder.
- **One appended line per event_id not already in the output file.** Running
  it twice adds nothing. Earlier lines are never rewritten, so scored events
  survive the store's 20-session quote pruning.
- **It prints the table above** for every rule version in the file.
- **Cadence:** at least once every 20 sessions, before quotes are pruned. By
  hand on Fridays is enough. A timer, or Codex's overnight runner, can call
  the same command later, after you approve that separately.

## Weekly AI review (optional, on the Claude plan)

`backend/scripts/radar_outcomes_review.py outcomes.jsonl --since <date> --out review.json` picks the four
events that kept going most and the four that reversed most at +60 min. It asks one Copilot Lab research
job what set them apart (news timing, sector or group participation, time of day), with citations and at
most two testable ideas for a later rule version.

- **Plan only.** It runs on the owner's subscription (`RESEARCH_AUTH=plan`); any other setting is
  refused, and a result that did not sign in with the plan is discarded.
- **Where it runs.** Plan mode runs only against a local database, so this is a Mac step, not a server
  job.
- **What it saves.** Nothing in the app. The review goes to `--out`.
- **What it is.** It sees outcomes, so it is hindsight: input to the next rule version, never a change to
  the current one or its decision. `--dry-run` prints the question without running a job.

## Deliberately not building

- No API route, screen or phone message. The October 28 repair adds two
  append-only metadata tables in the existing Radar SQLite store; results and
  session receipts go to one JSONL file plus a printed table.
- No replay of past passes, no threshold search and no sector-relative
  second outcome. One benchmark (SPY) keeps it legible.
- No integration with ResearchStore or the overnight runner. Codex can wrap
  the command as-is.
- No timer in this change.

## What gets built

- `backend/scripts/radar_outcomes.py`, roughly 150 lines, reusing
  `radar_store`, `radar_movers` and the rules' quote check.
- `backend/tests/test_radar_outcomes.py`: a synthetic store with hand-worked
  returns. It covers signing, horizon matching, the Movers and random
  comparisons, exclusions, appending to the output, idempotence, per-version
  separation and read-only opening.
- One short paragraph in `docs/radar.md` linking here.
- Classification: tier 0/1 (a read-only research script). The PR is for your
  review; nothing is activated.

## Limits to keep in mind

- **About 8 events a session, roughly half of them group events.** Twenty
  sessions is roughly 80 stock events, enough to spot a large difference, not
  a small one.
- **169 tracked symbols, regular hours only, last-trade prices.** The spread
  is not modelled.
- **"Kept going" is not "tradable".** Movers is the fair comparison because
  it is the free alternative you already have.
- **Your ratings stay the other half of the pilot.** This measures timing,
  not whether an event was useful to you.

## October 28 evidence-accounting repair

The recorder writes an immutable detection receipt after each recorded pass,
including failed/skipped detection and successful passes with **zero events**.
A missing receipt (including a crash after event insertion) is unknown, never
success. Only the live runner supplies `origin=live`; replay/default callers
cannot qualify. Each receipt points to a content-hashed snapshot of the actual
rule parameters and full universe, and records the calendar hours used. This
is operational provenance, not a cryptographic attestation against an operator
with database write access.

The outcome-blind census (`--census-only`, with the existing store and `--out`
arguments) reads metadata only and writes nothing. It reports every recorded
date before today and absent weekdays since the first recorded date; absent
dates have unknown calendar status, not inferred holidays or successful days.
A qualifying session requires consistent hours/configuration, successful live
receipts for all passes, unique event-to-pass provenance and every scheduled
minute slot. Timestamp rounding to the nearest minute tolerates scheduler jitter;
duplicates never replace a missing slot. Early closes use recorded hours.
Failures, partial days, replay and legacy rows remain explicit exclusions.
This strict completeness definition is fixed before inspecting outcomes.

`radar-outcomes-v2` appends session records as well as event records to the
existing JSONL output. Sessions without events count toward the 20-session gate.
The first 20 qualifying dates define the review window; later observations do
not repeatedly change that verdict. Configurations that reuse one version label
with different rule parameters or universe bytes cannot be pooled. The scorer
uses each event's recorded universe, never today's membership. Existing v1
scorer output stays unchanged and lacks verification; it cannot qualify merely
because it is already in the file. The optional review reader skips session rows
and events from unverified sessions. No return threshold, benchmark, horizon,
bootstrap rule, provider request, timer or trading policy changes here.

**Existing evidence:** the October 28 read-only audit found four completed
recorded dates (October 22, 23, 26, 27), 18 persisted v0 events on the latter two,
and no detector receipts. Thus **zero existing sessions can be certified by this
repair**. This is missing provenance, not evidence that those events were bad.
No replay or inferred success is used to restart their clock retroactively.
The first qualifying full session after an approved rollout starts the verified
count; a calendar date for the verdict cannot yet be promised.

**Rollout boundary:** implementation is not deployment. First writable opening
adds `detection_config` and `detection_receipt` to the Radar SQLite file. Earlier
binaries reject unknown tables, so rollback requires a receipt-aware binary or a
pre-upgrade backup restored through an explicitly approved recovery procedure.
Do not delete the new tables or alter the production store during verification.
Read-only census of an old store performs no migration. The journal database is
not involved. The PR remains for owner review/merge; no activation is implied.
