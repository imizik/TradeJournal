## Morning report

**What I investigated.** I compared the two questions you named against the data
that actually exists:

- **Your option exits.** The October 21 audit found the money goes after the
  first hour: −$17,558 on trades held from one hour to the close, and 53 losers
  that had been up 10% in their first hour. It never simulated a different exit.
  Three alerts based on that audit are now live (give-back, held an hour,
  expiry day). Nobody has checked whether following them would have kept money.
  Your trades, fills and the option minute bars needed to answer that already
  exist.
- **Recovery and relative strength with peer confirmation.** The Factory
  already tested the recovery swing: it failed the screen (t = 0.73 once trades
  in the same week are counted together). The Factory has been paused since
  October 16 as off-goal. Peer confirmation needs a peer group in the screen
  period (July 2023 to September 2024). The bar cache only holds the 18 core
  names and SPY there. QQQ, IWM and the other 40 names start in January or
  March 2026.

I picked **exits**. The evidence is stronger, the dollars are larger, and the
answer bears directly on the end goal's first proof (do the alerts help?).

**What the evidence showed.** Nothing yet on real trades. The question is
frozen, and the code is written and tested:

- For each past trade, the code replays the option's minute bars.
- It finds the moment each live alert's condition was met.
- It sells everything still open at the next minute's open, less a spread
  haircut.
- It compares that with what you actually did.
- It also compares the alert's moment with a random minute of the same trade.
  That is the "random entry" yardstick turned around for exits.

**What was rejected.**

- **Peer-confirmed recovery as a Factory candidate now.** The data does not
  cover the screen period, and the Factory is paused. I did not spend any
  Factory budget, run a factory week or touch the ledger.
- **Treating the audit's halves as a clean test.** The alert thresholds came
  from an audit that read both halves, so any historical result is
  consistency, not confirmation (see the protocol).

**What still looks interesting.**

- Whether the give-back rule's moment beats a random exit. If it does not, the
  money is in "get out sooner", not in the alert. That would change what the
  alert should say.
- The expiry-day rule. Expired-worthless trades cost $13.5k in the audit, and
  this rule is the easiest to follow.

**What data would most improve this.** Historical option bid/ask quotes. The
replay uses trade prints and a guessed 3% half-spread (stressed at 9%). The
live alert marks at the midpoint. See [Data gaps](#data-gaps).

**The single best next experiment.** Approve the one read-only extract below
and run the study once. It takes minutes. Then let the frozen code score
every trade from October 20 onward as the prospective test. The first review
comes at 30 give-back alerts or January 29, 2027, whichever is first.

### C1: the live alerts as mechanical exits (prepared, not run)

| | |
|---|---|
| Hypothesis | Closing the whole position when a live alert's condition is met would have kept more money than your actual exits |
| Why it might work | The audit: losers are held, green trades are ridden back through entry, short-dated options are left to expire. An exit at the alert caps exactly those paths |
| Instruments | Your closed and expired long option trades, 2025-07-10 to 2026-10-19 (the audit's 1,528, less exclusions the run counts) |
| Data | Journal fills (minute timestamps). Alpaca option 1-minute trade bars from the local cache, or fetched with `--fetch` for windows the Mac never cached. The local cache holds about 760 contracts expiring before March 2026 against roughly 1,178 exploration-half trades, so expect fetches |
| Rules | Give-back: armed at ≥ +10% and ≥ $50, exit at ≤ +3%. Held an hour: exit 60 regular-session minutes after first entry, entry day only. Expiry day: exit at 14:30 ET (11:30 on half days) on expiration |
| Execution | Decide at a bar's close, sell at the next bar's open within 5 minutes, otherwise the actual exit stands |
| Costs | 3% of price off the sell (minimum $0.01 a share); stress 9% |
| Benchmarks | Your actual exits; the same trades exited at 200 random judged minutes each |
| Results | **Not run.** Synthetic fixtures only |
| Validation status | Exploratory. Neither historical half is untouched for these thresholds. The clean test is prospective |
| Why results could mislead | Trade prints rather than midpoints, so the spread is guessed. A mechanical exit is not what an alert does: you decide, so this bounds full compliance. Dollars are driven by size, so return on premium is the size-neutral check. Long options decay, so almost any earlier exit can look good; that is why the random-minute benchmark exists |
| Decision rule | Fixed in the protocol: eligible for prospective testing only if the saving's 98.33% interval is above 0, both halves agree, it survives the stress cost and it beats random exits. A saving without beating random means "investigate: exit sooner". Otherwise reject |

## What the eventual unattended runner needs

For Codex's overnight infrastructure. This lane writes no scheduler, job or
ledger of its own.

1. **Permission:** one read-only extract per run:
   `python -m scripts.exit_counterfactual_study extract --ssh ubuntu@<vps> --out <private dir>/trades.json`.
   It runs `BEGIN READ ONLY; COPY (...) TO STDOUT` as `postgres` and selects
   only trade, fill, tradefill and account type. Better still: run it on the
   VPS as the `tj_app` role, or through a read-only endpoint. The output is
   personal financial data; keep it out of git and artifacts.
2. **Market data:** the Alpaca option-bar cache (read), plus `--fetch` with the
   existing Alpaca keys for missing windows. Market data only, no account or
   order endpoints.
3. **Run:** `python -m scripts.exit_counterfactual_study run --trades … --cache backend/data/alpaca_cache --out <dir> [--fetch]`.
   It is deterministic (seed 20261024) and writes `results.json` (aggregates)
   and `trades.jsonl` (per trade, personal).
4. **Stop conditions:** one historical run per protocol id. The prospective
   review happens once, at 30 give-back alerts or 2027-01-29. A changed
   constant is a new protocol id, recorded alongside this one, never an
   overwrite.
5. **Output for the morning:** `results.json` → this report's format: the
   decision per rule, the dollar difference with its interval, the random-exit
   comparison, and the exclusion counts.
